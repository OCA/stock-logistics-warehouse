This module extends ``stock_vlm_mgmt`` to communicate with Kardex
Vertical Lift Modules (VLMs) over a TCP socket connection. It supports
put, get, count and tray release operations from Odoo.

Request templates, field separators and response layouts are
configurable per Kardex location. The connector exchanges UTF-8 messages
terminated by CRLF and processes intermediate device events until a
final response is received. Response task identifiers are not required
or checked.

Tray calls send the command without waiting for a device response.

Configuration
=============

Configure the VLM connection on the stock location and select **Kardex**
as the vendor. Set the following fields to match the JMIF configuration:

- **Socket Message Format**: a Python format string with named
  placeholders, not a Python expression. For example:

  .. code:: text

     {task_type},{task_id},{address},{carrier},{pos_x},{pos_y},{qty},{info1},{info2},{info3},{info4}

  All placeholders must exist in the request data. Numeric formatting
  such as ``{qty:.0f}`` is supported. The template does not
  automatically convert operation names to device codes or quantities to
  integers.

- **Separator**: separator used in requests and responses, for example
  ``;``. After formatting the request, every comma is replaced with this
  separator, including commas inside field values.

- **Socket Format**: ordered response field names, separated by the
  configured separator. For example, with ``;``:

  .. code:: text

     task_type;task_id;address;carrier;pos_x;pos_y;qty;info1;info2;info3;info4

  This layout controls response parsing independently of the request
  template. Missing values become ``None``; extra values are ignored.

- **Response Code Key**: name of the response field containing the
  device code, for example ``task_type`` in the layout above.

A single CRLF (``\r\n``) terminator is appended automatically to each
request. JMIF responses must also use CRLF as the message delimiter.

Configure JMIF to send a final confirmation after arrival: the connector
always treats code ``203`` as intermediate. A setup that ends the
operation at arrival without sending a final response is not supported
by this workflow.

Usage
=====

Run the put, get, count or tray release operation through the VLM
workflow. When a response is expected, the connector processes one
response per socket read (up to 1024 bytes). Each read is assumed to
contain a complete response; fragmented messages and multiple messages
in one read are not reassembled or separated.

The following device events keep the connector waiting:

- ``201``: request accepted and queued.
- ``202``: request processing started.
- ``203``: carrier arrived; operator confirmation is still expected.

Any other code ends the wait. Code ``0`` indicates success. Device code
``101`` is mapped to ``-4``, and ``107`` to ``-5``, in the configured
response code field. Other codes are returned unchanged. A missing or
empty response code is returned as ``-999``.

Connection refusal returns ``code = -1``, connection closure before a
final response returns ``code = -2``, and a receive timeout returns
``code = -3``. These connection status dictionaries also include the
submitted ``task_id``. Device response identifiers are not compared with
the submitted identifier.

A positive connector timeout limits each socket read, not the total
operation time. With a timeout of zero, reads can block indefinitely.
Tray calls skip response reading and return immediately after sending
the request.
